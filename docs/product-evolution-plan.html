План эволюции продукта

Как Slotly переходит от набора лабораторных сценариев к связному MVP с двумя ролями — клиентом и владельцем организации — и какие технические решения для этого приняты. Документ составлен до реализации по итогам аудита кода и дополняется по мере работы.

Граница этапа. Всё описанное здесь работает локально на устройстве: демо-вход, локальное хранилище, локальные напоминания. Это не production-backend и не система безопасности. Серверная часть (фаза B) только спроектирована.

Фазы

Фаза A (реализуется сейчас): демо-аутентификация, роли клиента и владельца, локальное хранилище с версией схемы, детерминированные seed-данные, отзывы и рейтинги, избранное, управление организацией, услугами, ценами и фотографиями, аналитика владельца, локальные напоминания, жесты в продуктовых сценариях, тесты и документация.

Фаза B (только границы и roadmap): Django/DRF API, PostgreSQL, серверная аутентификация с access/refresh-токенами, серверная проверка прав, мультитенантная изоляция, объектное хранилище фотографий, FCM, серверный планировщик, агрегация аналитики, аудит, резервное копирование, мониторинг. Подробности — в плане развития.

Решения

Р1. Состояние и внедрение зависимостей: оставить ChangeNotifier и AppScope

  • Проблема. Появляются сессия, роли, несколько общих источников данных (каталог, записи, отзывы, избранное, аналитика), которые должны обновляться согласованно.
  • Решение. Сохранить ChangeNotifier + ListenableBuilder и конструкторное внедрение через AppDependencies/AppScope. Единый источник истины — локальная база AppDatabase, которая сообщает об изменениях; контроллеры перечитывают данные через репозитории.
  • Почему подходит MVP. Текущий код уже так устроен и покрыт тестами; участники знают этот подход; нет кодогенерации.
  • Какую production-проблему предотвращает. Экраны не создают источники данных сами — HTTP-реализации подставляются в одном месте; нет глобальных синглтонов, которые мешают тестам.
  • Стоимость. Немного шаблонного кода в контроллерах (загрузка, ошибка, данные) — вынесено в один общий класс.
  • Альтернатива. Riverpod (или provider).
  • Почему отклонена. Перевод работающих экранов не даёт измеримой пользы: сессия одна, зависимостей мало, тесты уже подменяют зависимости через конструктор.
  • Когда вернуться. Если появятся десятки экранов с общими асинхронными данными, кэширование запросов к API, отмена запросов при уходе с экрана.

Р2. Навигация: Navigator с корнем по роли

  • Проблема. Клиент и владелец видят разные оболочки; недоступные маршруты должны блокироваться; напоминание должно открывать конкретную запись.
  • Решение. Корневой виджет выбирает экран по состоянию сессии: Welcome/вход, оболочка клиента или оболочка владельца. При входе и выходе стек полностью заменяется. Маршруты владельца строятся только внутри его оболочки, а права дополнительно проверяет слой данных. Переход из напоминания — через navigatorKey и id записи.
  • Почему подходит MVP. Один deep link (запись из напоминания) и две оболочки не требуют декларативного роутера; лабораторные требования (типизированная передача Service в конструктор) сохраняются.
  • Какую production-проблему предотвращает. После выхода назад нельзя вернуться в чужую оболочку: стек заменяется, а не дополняется.
  • Стоимость. Ручная обработка одного deep link.
  • Альтернатива. go_router с redirect по роли и StatefulShellRoute.
  • Почему отклонена. Перепись всех маршрутов и тестов навигации ради одного deep link; URL-маршруты на Android сейчас не нужны.
  • Когда вернуться. Web-версия, App Links, несколько внешних точек входа (ссылки из SMS, e-mail), вложенная навигация внутри вкладок.

Р3. Локальное хранилище: версионируемый JSON-документ

  • Проблема. Вход, отзывы, избранное, правки организации и фотографии должны переживать перезапуск.
  • Решение. AppDatabase держит снимок данных в памяти и сохраняет его одним JSON-файлом в каталоге приложения: запись во временный файл и атомарное переименование, все записи последовательно через одну очередь. В файле есть schemaVersion; при загрузке применяются миграции по цепочке. Тесты используют хранилище в памяти. Даты — ISO-8601 в UTC, отображение — в локальной зоне.
  • Почему подходит MVP. Демо-объём — сотни записей; аналитика всё равно считается в Dart по спискам; один писатель в одном изоляте — нет конкурентных обновлений. Нет кодогенерации и нативных библиотек, CI не усложняется.
  • Какую production-проблему предотвращает. Потерю данных при сбое во время записи (атомарное переименование) и поломку при обновлении приложения (версия схемы и тестируемые миграции). Репозитории не знают о формате хранения — HTTP-версия заменит их без изменений экранов.
  • Стоимость. Ручные toJson/fromJson для моделей; весь снимок перезаписывается при каждом изменении (для сотен записей — миллисекунды).
  • Альтернатива. Drift (SQLite) — типобезопасные запросы, миграции и индексы.
  • Почему отклонена. Кодогенерация (build_runner), нативные библиотеки SQLite (+~1,5 МБ на ABI), больше кода маппинга; выигрыша по скорости на таком объёме нет. sqflite отклонён по той же причине и из-за ручного SQL-маппинга.
  • Когда вернуться. Тысячи записей на устройстве, выборки с индексами, офлайн-кэш серверных данных с синхронизацией, доступ из фонового изолята.

Р4. Модель предметной области: организация как верхний контекст

  • Проблема. Отзывы, рейтинг, избранное, аналитика и права владельца относятся к организации, а каталог построен вокруг услуг.
  • Решение. Добавить Organization со стабильным organizationId; услуга и специалист принадлежат организации; запись связывает клиента, организацию, услугу и специалиста. Существующий путь «услуга → детали → форма записи» сохранён, а каталог получает переключатель «Организации / Услуги».
  • Почему подходит MVP. Лабораторные сценарии поиска услуг продолжают работать; новый уровень добавляется, а не переписывает старый.
  • Какую production-проблему предотвращает. Мультитенантность: каждая сущность знает свою организацию, поэтому проверка «владелец видит только своё» — простое сравнение id.
  • Стоимость. Услугам и специалистам добавляется поле, демо-каталог переезжает в seed.
  • Альтернатива. Отдельная таблица OrganizationMembership с ролями (владелец, администратор, мастер).
  • Почему отклонена. Сейчас у организации ровно один владелец; поле organizationId у пользователя-владельца покрывает сценарий (YAGNI).
  • Когда вернуться. Несколько сотрудников с разными правами, один человек в нескольких организациях.

Р5. Демо-аутентификация

  • Проблема. Нужны вход, выход, роли и восстановление сессии без backend.
  • Решение. Демо-аккаунты в seed; пароль хранится как SHA-256 с солью (пакет crypto); сессия — id пользователя в локальной базе. В интерфейсе и документации явно сказано, что это прототип.
  • Почему подходит MVP. Повторяет форму будущего серверного входа (логин → пользователь с ролью → сессия), но без сервера.
  • Какую production-проблему предотвращает. Экраны и репозитории уже получают текущего пользователя из одного SessionController — при переходе на токены меняется только он.
  • Стоимость. Одна зависимость (crypto, команда Dart).
  • Альтернатива. Сразу Firebase Auth или собственный сервер.
  • Почему отклонена. Обязательный внешний сервис и сеть для лабораторной демонстрации; риск сроков.
  • Когда вернуться. Фаза B: Django/DRF, Argon2id на сервере, короткий access token, refresh token в secure storage, отзыв сессий, rate limiting.

Р6. Права: политика доступа в слое данных

  • Проблема. Скрытие кнопок не защищает от прямого вызова метода.
  • Решение. Класс AccessPolicy с перечнем действий (AppAction); каждый репозиторий перед операцией вызывает policy.require(...) с текущим пользователем и организацией ресурса и бросает AccessDeniedException. UI использует ту же политику, чтобы не показывать недоступное.
  • Почему подходит MVP. Одна таблица правил, которую легко протестировать параметризованно для всех ролей и действий.
  • Какую production-проблему предотвращает. Межтенантный доступ (владелец A → данные B) и подделку действий (владелец пишет отзыв от имени клиента).
  • Стоимость. Вызов политики в каждом методе-мутаторе.
  • Альтернатива. Проверки прав только в UI или «ролевые» репозитории (отдельные классы для клиента и владельца).
  • Почему отклонена. Первое небезопасно, второе дублирует код и всё равно требует проверок принадлежности ресурса.
  • Когда вернуться. На сервере (фаза B) та же матрица станет DRF permissions и фильтрацией queryset по организации.

Р7. Аналитика: чистый калькулятор над исходными данными

  • Проблема. KPI должны считаться из записей, отзывов и избранного, а не храниться готовыми числами.
  • Решение. Чистая функция-калькулятор (без Flutter) получает записи, отзывы и избранное одной организации и период 7/30/90 дней и возвращает все показатели и ряды для графиков. Репозиторий аналитики проверяет права и кэширует результат до следующего изменения данных.
  • Почему подходит MVP. Формулы тестируются на маленьких наборах данных; экран не пересчитывает ничего при перерисовке.
  • Какую production-проблему предотвращает. Рассинхронизацию сохранённых агрегатов с данными; утечку чужих показателей.
  • Стоимость. Пересчёт при каждом изменении данных — сотни элементов, незаметно.
  • Альтернатива. Хранить агрегаты (рейтинг, счётчики) и обновлять их при изменениях.
  • Почему отклонена. Риск расхождений и лишняя логика инвалидации без выигрыша на таком объёме.
  • Когда вернуться. На сервере: материализованные агрегаты по дням и фоновые пересчёты.

Р8. Графики: собственные виджеты

  • Проблема. Нужны столбцы по дням/неделям, горизонтальные полосы (специалисты, услуги) и распределение статусов, с текстовой альтернативой.
  • Решение. Два небольших виджета на стандартных Row/Container: вертикальные столбцы и горизонтальные полосы, с подписью для TalkBack и переключателем «таблица».
  • Почему подходит MVP. Все графики — столбчатые; виджеты дают Semantics и тёмную тему без настройки, проверяются golden-тестами.
  • Какую production-проблему предотвращает. Зависимость от сторонней библиотеки с собственной темизацией и ограниченной доступностью.
  • Стоимость. ~200 строк кода.
  • Альтернатива. fl_chart (MIT, активно поддерживается).
  • Почему отклонена. Для набора столбчатых графиков избыточна; доступность пришлось бы добавлять вручную поверх CustomPainter.
  • Когда вернуться. Линейные графики с интерактивными подсказками, масштабирование по времени, десятки рядов.

Р9. Напоминания: локальные, без точных будильников

  • Проблема. Клиенту нужны напоминания накануне, в день визита и за час.
  • Решение. flutter_local_notifications + timezone + flutter_timezone. Чистый ReminderPlanner вычисляет время и детерминированные id; координатор синхронизирует запланированные напоминания с активными записями клиента после каждого изменения. Режим inexactAllowWhileIdle — без разрешения на точные будильники.
  • Почему подходит MVP. Работает без сервера и Firebase; допуск в несколько минут для напоминания приемлем.
  • Какую production-проблему предотвращает. Дубли (одинаковые id перезаписываются), «осиротевшие» напоминания отменённых записей (полная синхронизация), неправильное время при смене часового пояса.
  • Стоимость. Нативная настройка Android (desugaring, ресиверы), запрос разрешения на Android 13+.
  • Альтернатива. FCM-push с серверным планировщиком.
  • Почему отклонена. Требует backend и Firebase; не нужно для напоминаний о собственных записях на одном устройстве.
  • Когда вернуться. Изменения записи владельцем, несколько устройств, переустановка приложения.

Р10. Фотографии: файлы в каталоге приложения

  • Проблема. Владелец добавляет до пяти фотографий; исходный URI галереи может стать недоступным.
  • Решение. image_picker с уменьшением (до 1600 px, качество 85), копия файла в управляемый каталог приложения, в базе — только путь. Отображение с cacheWidth, при ошибке — заглушка. Демо-фотографии — встроенные иллюстрации.
  • Почему подходит MVP. Нет бинарных данных в JSON-файле; лимит и формат проверяются в репозитории.
  • Какую production-проблему предотвращает. Потерю фото при очистке галереи, раздувание базы, загрузку полноразмерных изображений в память.
  • Стоимость. Две зависимости (image_picker, path_provider).
  • Альтернатива. Хранить изображения в базе (base64).
  • Почему отклонена. Каждая запись снимка перезаписывала бы мегабайты.
  • Когда вернуться. Фаза B: объектное хранилище и загрузка по presigned URL.

Р12. Seed-данные: детерминированный генератор

  • Проблема. Нужны сотни правдоподобных записей и отзывов за 90 дней для графиков и проверки изоляции.
  • Решение. Генератор с фиксированным зерном Random, привязанный к дате первого запуска (через Clock). Seed выполняется один раз, версия seed хранится в базе; повторный запуск ничего не дублирует.
  • Почему подходит MVP. Одни и те же данные в тестах (фиксированные часы) и правдоподобные даты на устройстве.
  • Какую production-проблему предотвращает. Нестабильные тесты и захардкоженные «итоговые» числа.
  • Стоимость. Генератор ~300 строк.
  • Альтернатива. Статический JSON с готовыми записями.
  • Почему отклонена. Даты «устаревают»: через месяц график за 7 дней опустеет.
  • Когда вернуться. Если понадобится вручную выверенный набор для конкретного демонстрационного кейса.

Порядок работ

  1. Хранилище, seed, часы, контракты репозиториев.
  2. Демо-вход, сессия, роли, матрица прав, навигация по роли.
  3. Организации, рейтинги, отзывы, избранное, жесты.
  4. Оболочка владельца, редактор организации, услуги и цены, фото.
  5. Аналитика, графики, фильтры, текстовая альтернатива.
  6. Напоминания, разрешения, перенос и отмена, переход из напоминания.
  7. Полировка интерфейса, тёмная тема, доступность, производительность, скриншоты.
  8. Полный набор тестов, документация, отчёты участников, сборка.

После каждого этапа: format, analyze, тесты, проверка diff, запись в CHANGELOG и отдельный коммит.
